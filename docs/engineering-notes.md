# 工程问题与回归措施

## GCC 位于中文目录时无法找到汇编器或运行库

现象：编译器主程序可执行，但最小 `int main(){return 0;}` 仍在寻找 as 或链接运行库时失败。

最小复现排除了项目代码与线程库。逐步检查实际工具/库位置后，发现 GCC/Binutils 的安装前缀在本机非 ASCII 路径下被错误解释。单纯增加 include 路径无效，因为失败发生在工具发现和链接阶段。

本地脚本显式设置相对 `GCC_EXEC_PREFIX`、`-B` 和 `-L`，从固定项目工作目录执行。该修复局限于对应 Windows 便携工具链；通用工程入口仍为 CMake。回归依次为最小程序、全部目标编译、完整测试及中文绝对路径 CLI。

## 可执行程序无法读取中文绝对路径

现象：相对数据路径可运行，中文绝对路径失败；同一文件存在，说明不是数据损坏。

定位：先用人工构造的 4 个二维点排除检索算法，再比较传入参数与文件打开环节。Windows CRT 的窄 argv 和默认窄文件路径存在编码损失。

修复：wmain → 显式 UTF-8 转换 → filesystem::u8path。只改控制台显示编码不能修复参数与文件系统边界。

回归：`scripts/check_cli.py` 创建临时中文目录，分别检查三个查询引擎及中文 CSV 输出，并在结束时删除夹具；同时验证输入覆盖保护和非法参数拒绝。

## 快速实验可能覆盖完整实验的汇总

现象：快速运行后，顶层汇总与较早完整报告的运行身份不一致，无法可靠对应结论与原始数据。

最小复现使用人工 CSV 与假运行身份，不必反复运行耗时 benchmark。问题在于正式与快速协议共享顶层发布路径，且失败运行也可能留下“最新”状态。

修复：所有运行先写唯一 run 目录；成功完整运行才更新正式汇总，smoke 写独立文件。保存协议、状态、输入/程序哈希与运行身份。失败运行保留诊断，但不能冒充成功数据。

`regression_result_isolation()` 检查完整、快速、失败三条路径及内容身份。公开历史数据固定在 `benchmarks/2026-10-23/`，新实验仅写被忽略的 `results/`。

## 发布打包原则

源码、测试、复现协议与必要历史实验进入版本控制；二进制、工具链、下载数据、缓存、临时路径和调试夹具不进入版本控制。历史 CSV 保持原始字节；来源清单导出为相对工程路径，并明确 Python/CMake 打包更新不等于重新测量性能。
